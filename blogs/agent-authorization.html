Agent Security · Part 1

Who Is the Agent Acting For?

Every authorization system we have was built on an assumption agents quietly break: that behind each request there is one human, and that the system can tell who they are. Once software starts reasoning and calling tools on someone's behalf, that assumption stops holding — and most of the hard problems in agent security follow from it.

Arnab KarSarkar

The demos are easy. An agent reads a ticket, looks up an account, drafts a reply. Nobody asks hard questions at that stage, because nothing it touches matters very much.

The questions arrive the first time an agent is allowed to write. Issue the refund, update the record, send the message, revoke the access. At that moment someone has to answer: by what authority did it do that? And when the answer is it had an API key in its config, you don't have an authorization model. You have a service account with a language model attached to it.

The confused deputy, with better grammar

The underlying pattern is old. A confused deputy is a program with more privilege than the party instructing it, which can be talked into using that privilege on the instructor's behalf. Agents are an unusually good deputy: they hold broad credentials, they take instructions in natural language, and they are built to be helpful.

What makes this sharper than the classic case is where the instructions come from. An agent's context is assembled from many sources — the user's request, retrieved documents, tool results, prior turns, memory. To the model, all of it is tokens. There is no structural separation between instructions I should follow and data I should reason about. We have parameterized queries for SQL. We have nothing equivalent here.

The practical consequence

If the content an agent reads can influence what it does, and the agent can act with real privilege, then anyone who can get text in front of it has partial control of those actions. Filtering helps at the margin. It does not change the shape of the problem.

Two answers that don't work

Give the agent its own service account

Simple to build, and it fails in the obvious direction. The account needs union privilege — everything any user of the agent might legitimately need — so every request runs with the permissions of the most privileged person the agent serves. A user who could never read a particular record asks the agent, and the agent happily reads it. The authorization check passed. It was just answering the wrong question.

Pass the user's token straight through

Better, and closer to right: now the agent can only reach what the user could reach. But there is no agent-level constraint left. A support agent and a finance agent acting for the same person have identical reach, because the only thing being checked is the human. The agent's own scope — what this agent is supposed to be for — isn't expressed anywhere.

Authority as an intersection

The model that holds is neither one alone. An agent should act with the intersection of two things: the authority delegated to it by the human it is acting for, and the scope it was provisioned with as an agent. 

    what the user can do          what this agent is for
    ────────────────────          ──────────────────────
    read accounts                 read accounts
    write accounts                read tickets
    read tickets                  draft replies
    approve refunds
    delete records

                    ∩

            effective authority
            ───────────────────
            read accounts
            read tickets
Neither the user's permissions nor the agent's provisioned scope is the answer on its own. The effective authority is what both allow.

This is not a new idea — it is delegation, and identity systems have modelled it for years through token exchange and on-behalf-of flows. What is new is how often it has to happen. A single agent run may touch six systems across several turns, and each of those calls needs to carry the right delegated authority rather than a standing credential that outlives the task.

Three properties matter in practice:

  • Short-lived. Credentials scoped to a task, not to a deployment. An agent that is idle should not be holding anything useful.
  • Checked at call time. Not once at session start. The relevant question is whether this action is permitted now, not whether the agent was trusted when it booted.
  • Dually attributable. Every action should name both the agent and the human it acted for. One without the other makes incidents unresolvable.

Counting the dangerous combination

The most useful tool I've found for reasoning about an agent's risk isn't a threat model document. It's a counting rule. An agent becomes dangerous when it holds all three of:

  1. Exposure to untrusted content
  2. Access to sensitive data or systems
  3. The ability to change state or communicate outward

Any two are usually survivable. An agent that reads untrusted web pages and can send email but holds no private data has little to leak. An agent with deep data access that only ever answers the person in front of it has no channel out. It is the third leg that turns a compromise into an incident.

What makes this framing useful is that it turns a vague feeling of risk into an architectural decision. If a design needs all three, you don't argue about whether it feels safe — you put a break in the chain at the point where the third leg appears.

The one control that holds structurally

Most defenses against prompt injection are probabilistic. Classifiers, pattern matching, instruction hierarchies, delimiters — each raises the cost of an attack and none of them closes it, because the attacker gets to adapt and the defender's surface is natural language. Published evaluations are consistent on this point: defenses that look strong against fixed test sets degrade sharply against attackers who know what they're facing.

A human approval step is different in kind. It cannot be argued around by a cleverer prompt, because the thing standing between the agent and the action isn't a model making a judgment. It's a person being asked a question.

That doesn't mean approving everything. It means grading by blast radius:

Action classTreatment
Read, reversible, low valueAutonomous
Write, reversible, boundedAutonomous with caps and audit
Irreversible, or moves money, or touches accessHuman approval on the step

The useful discipline is to decide the ceiling before building the capability. It is much harder to add a boundary to an agent that already has none than to design one in from the start.

Agents as entities, not features

The shift that changed how I think about this: as autonomy increased, orchestration stopped being the hard part. Getting agents to do the work became tractable well before the organizational questions did.

What remained hard was accountability. Who owns this agent. What is it allowed to do. Who answers for it when it does something wrong. Who notices if its behaviour drifts. These are not questions about model capability, and no amount of prompt engineering answers them.

The framing that helped

Treat an agent as an entity in the organization rather than a feature of an application. It has an owner. It has a defined scope of authority. Its actions are attributable, and its behaviour is reviewable. Once agents are modelled that way, most of the hard questions have familiar answers — because they are the questions organizations already know how to ask about people.

Where this leaves us

Prompt injection is not solved and may not be solvable in the form people want it solved. That sounds like a counsel of despair and it isn't, because it is the same position we occupy with every other class of software vulnerability. We do not assume our code is free of bugs. We assume it isn't, and we limit what a bug can reach.

The equivalent discipline for agents is to stop asking how to guarantee the agent won't be manipulated, and start asking what happens when it is. Narrow the authority. Shorten the credentials. Check at call time. Put a human on the irreversible step. Make every action attributable to both the agent and the person behind it.

None of that requires the model to be trustworthy. That is the point.
