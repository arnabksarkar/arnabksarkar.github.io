Agent Architecture

From Hundreds of Bots to One Orchestrator

May 2026 · Arnab KarSarkar · 6 min read

Since the launch of ChatGPT, the world changed and everyone rushed to build agents for enterprises... it felt productive. A team needs ticket triage, so you build a triage bot. Finance wants invoice lookups, so you build an invoice bot. IT wants password resets, so that becomes a bot too. Each one ships and each one works.

A year later there are a hundred of them. Nobody remembers which does what, two of them overlap, and a request that spans finance and IT cannot be finished by any single bot. This is bot sprawl. The picture below is the whole problem, and the whole fix.

Left: every capability is a sealed bot you must choose between. Right: one router reasons about the goal and calls skills as tools.

Why more bots stops scaling

The problem is not the count. It is that each bot is a sealed unit, so three things get worse with every one you add.

DimensionOne bot per taskSkills + orchestrator
DiscoveryYou must know which bot to call before you startYou state a goal; the router decides
Cross-boundary workA human stitches steps across bots by handOne plan spans skills automatically
ReuseEach bot reimplements shared capabilityA skill is written once, called by many
Adding capabilityOne more bot for users to learnOne more tool the router can pick

The core idea: skills map to tools

Separate two things the one-bot model fuses together: the capability and the thing that decides when to use it. A skill is a scoped capability with its own instructions, context, and allowed tools. It does one job and knows nothing about routing. The orchestrator is the only component that reasons about intent, and it sees every skill as just another callable tool.

The shift

Old: a user picks a bot, then the bot tries to do everything.

New: a user states a goal, and the orchestrator picks skills the way an agent picks tools.

Agents as tools, via MCP

Here is the piece that makes this compose instead of collapsing back into sprawl. A skill does not have to be a simple function. It can itself be an agent. The Model Context Protocol (MCP) gives a standard way to publish a capability and its contract, so an agent wrapped behind an MCP server becomes a tool any other agent can call through the same uniform interface. The caller never knows whether the thing it called was one function or a multi-step agent of its own.

To the orchestrator it is one tool call. Behind the MCP boundary, the skill runs its own multi-step agent.

That single property is what turns a flat list of skills into a layered system. A high-level skill can be built from lower-level skills without any of them knowing the others' internals.

How the orchestrator routes

With skills as tools, the top-level agent's job gets small: reason about the goal and break it into steps, route by calling skills as tools in sequence or in parallel, and review the results to decide whether to finish or take another step. The review step is also the natural place to put a human in the loop: pause before a consequential action, get approval, then continue with the same shared state.

The tradeoffs, honestly

This pattern is not free, and it is the wrong choice for a handful of unrelated automations. Where it costs you, and how to keep each cost in check:

CostWhy it happensHow to manage it
Added latencyNested model calls when a skill is itself an agentKeep hot paths shallow; cache; skip the router for known single tasks
Harder tracingOne request fans out across several skillsTrace across the whole graph from day one, not bolted on later
Routing errorsThe orchestrator is a model making a choiceStrong tool descriptions and a review step before actions
Shared stateSkills toward one goal need a consistent viewModel state deliberately instead of hiding it in one bot

When not to do this

If you have a few unrelated automations and no cross-boundary pain, you do not need an orchestrator. The one-bot model is simpler and faster, and simpler wins until it stops working. Reach for orchestration when the symptoms are real: users asking which bot to use, requests no single bot can finish, and the same capability built in three places.

Takeaways

  • Bot sprawl is an architecture ceiling, not an effort problem.
  • Separate capability from routing: a skill is a scoped capability exposed as a tool.
  • Use MCP to expose agents as tools. That is what lets skills compose into layers.
  • Keep the orchestrator thin: reason, route, review, with human approval at the review step.
  • Adopt the pattern when the symptoms are real, not before.
